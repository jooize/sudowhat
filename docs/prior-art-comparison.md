# sudowhat vs. prior-art macOS biometric-sudo projects

A comparison of sudowhat against the established landscape of Touch ID / Apple Watch `sudo` tooling on macOS. Every factual claim about a prior-art project is grounded in the structured source analyses; claims about sudowhat are grounded in its own source tree (`plugin/sudowhat_approval.m`, `plugin/SessionGuard.m`, `pam/pam_sudowhat.m`, `shared/SignatureVerifier.m`, `config/`, `README.md`).

## Landscape

Bringing biometrics to `sudo` on macOS has converged on three families of prior art. They differ in *where* they intervene, but they share one defining limitation, which sudowhat exists to remove.

**(a) PAM enablers — switch on biometric/watch auth for the existing sudo stack.** This is the bulk of the field. Apple's own closed-source `pam_tid.so` is the reference: a stock module wired in (on Sonoma+) by uncommenting `auth sufficient pam_tid.so` in `/etc/pam.d/sudo_local`, evaluating an Apple-internal companion-aware policy via `-[LAContext evaluatePolicy:options:error:]`. The community variants reimplement the same idea in a ~65–100-line Swift `.so`: Reflejo/pam-touchID (Touch ID via the private `LAPolicy(rawValue: 0x3f0)`), insidegui/pam-watchid and biscuitehh/pam-watchid (Touch ID *or* Watch via `LAPolicy.deviceOwnerAuthenticationWithBiometricsOrWatch`, aliased misleadingly as `deviceOwnerAuthenticationIgnoringUserID`). inickt/pam_wtid is the odd one out — it ships no auth code at all, instead binary-patching the policy immediate inside Apple's own `pam_tid` (the constant `1` → `4`, biometrics → biometrics-or-watch) and re-signing it ad-hoc. What unites this family: the line is `auth sufficient`, so the module can only *add* a convenience factor and never tighten the bar; on any failure or unavailability it returns `PAM_IGNORE`/failure and PAM falls through to the password prompt.

**(b) sudo forks — intervene inside sudo itself.** mattrajca/sudo-touchid is the lone representative: a full fork of Apple's `sudo 1.8.17p1` (2016) that registers a new standalone `touchid` auth method in `sudo_auth.m`, evaluating the undocumented policy `0x3f0` and busy-spinning a `CFRunLoop` until the LA reply fires. It runs *before* PAM and disables every other standalone method, so unlike the PAM family it is fail-closed — but at the cost of shipping a frozen, years-stale `sudo` that misses every post-2016 CVE fix.

**(c) installer / persistence wrappers — don't authenticate, just configure and re-apply.** artginzburg/sudo-touchid is a ~433-line Bash installer that enables Apple's `pam_tid.so` and, crucially, *keeps it enabled* — writing to `/etc/pam.d/sudo_local` on macOS 14+, or installing a `RunAtLoad` LaunchDaemon to re-apply the `/etc/pam.d/sudo` edit on every boot for older systems.

**The common thread, and the gap.** Every one of these solves the same problem — "let me approve `sudo` with my finger or my watch instead of typing a password" — and the analyses converge on the same shared friction: the `/etc/pam.d/sudo` edit is wiped by OS updates (per every PAM-family analysis that hand-edits `sudo` rather than using `sudo_local`); Touch ID does not fire over SSH; it historically broke in tmux/screen without `pam_reattach`; and — the recurring security complaint — *the prompt is generic and hides which command is actually being elevated*. The deeper worry the analyses raise is that a malicious local process can fire a prompt the user reflexively approves, with aliases or wrappers masking the real command. Per the analyses, **not one prior-art project shows the resolved command, and not one binds approval to the active console user** — the two gaps that define sudowhat's purpose.

## Project-by-project

### Apple `pam_tid.so` (system module)
The stock baseline. Creates an `LAContext` and calls the private `-[LAContext evaluatePolicy:options:error:]` with an Apple-internal, companion-aware policy (SEP/companion bootstrap selectors like `bootstrapSEPWithUID:` are present in the binary), brokering Touch ID and, on capable hardware, Apple Watch. Wired in as `auth sufficient` via `/etc/pam.d/sudo_local`, so it survives OS updates and degrades to `pam_opendirectory` password over SSH. **Strengths:** maintained by Apple, platform-signed, update-safe `sudo_local` enablement, prearms the sensor (`prearmTouchIdWithReply:`) to cut perceived latency before the sheet appears. **Weaknesses (per analysis):** the sheet shows only a generic "sudo is trying to …" reason and never the argv; no independent console-user gate (trusts LA's own session binding); sudo's ~5-minute timestamp cache means one approval silently covers later commands; fail-open means the biometric requirement is trivially removed.

### Reflejo/pam-touchID (Swift PAM module)
A single-file Swift `.so` implementing `pam_sm_authenticate`: `canEvaluatePolicy` gate, then `evaluatePolicy(_:localizedReason:)` blocking on a `DispatchSemaphore`. Policy is the private `LAPolicy(rawValue: 0x3f0)` (`kLAPolicyDeviceOwnerAuthenticationIgnoringUserID`) with a public-constant fallback. Installed by hand-editing `/etc/pam.d/sudo`. **Strengths:** clean dependency-free template; defensive `?? .deviceOwnerAuthenticationWithBiometrics` fallback; `PAM_IGNORE` on `-A`/`--askpass`. **Weaknesses:** generic static `reason=` string; the IgnoringUserID policy explicitly disregards which user owns the enrollment (textbook reflexive-approval); no signing; manual edit reverted by updates; pinned `darwin20.1.0` build target.

### insidegui/pam-watchid (Swift PAM module)
~100 lines, the same semaphore-bridged pattern, using `deviceOwnerAuthenticationWithBiometricsOrWatch` so an unlocked Watch satisfies auth for free. Notably the **best remote-context hygiene in the field**: it checks `SSH_TTY` up front and returns `PAM_IGNORE`, and likewise for `-A`/`--askpass`. **Strengths:** explicit SSH detection, well-behaved across all four PAM entry points (the unused ones explicitly `PAM_IGNORE`), no C bridging header. **Weaknesses:** no console-user binding; static reason; an `NSRegularExpression` built on attacker-influenceable argv with a `Character`-count vs. `NSString`-length range bug; x86_64-only `10.15` target; unsigned.

### biscuitehh/pam-watchid (Swift PAM module)
A Watch-variant fork in the Reflejo lineage; ~65 lines via `@_cdecl` exports and inline PAM constants, `deviceOwnerAuthenticationWithBiometricsOrWatch` (aliased, vestigially, as `deviceOwnerAuthenticationIgnoringUserID`). **Strengths:** the cleanest minimal Swift-PAM template; Watch support for free; `PAM_IGNORE` graceful degradation. **Weaknesses:** semaphore wait with **no timeout** (a hung LA prompt stalls sudo indefinitely); no console gate; static reason; unsigned in world-writable `/usr/local/lib/pam` while placed *first* as `sufficient` (a malicious replacement = instant passwordless root); x86_64-only, unmaintained since 2020.

### inickt/pam_wtid (binary-patch installer)
Writes no auth code. `patch.py` locates the call to `_LAEvaluatePolicy` inside Apple's `/usr/lib/pam/pam_tid.so.2`, back-tracks to the register-load that sets the policy argument, and flips the immediate from `1` (biometrics) to `4` (biometrics-or-watch), then ad-hoc re-signs and installs as `pam_wtid`. **Strengths:** the byte-search-and-backtrack technique is robust across recompiles; ships regression fixtures (real `pam_tid` from 11.6.1/12.1, x86_64/arm64e) with a `make test`; self-validating install (`make working` smoke-tests `sudo -v -k` and auto-rolls-back). Its key insight: reusing Apple's binary — whose private options dict correctly binds the `LAContext` to the invoking user under root — is *why watch-as-root works* where naive Swift forks reported "no fingerprints enrolled." **Weaknesses:** no console gate; generic prompt; `auth sufficient` + ad-hoc signature means a forged success grants root with no password fallback; edits `/etc/pam.d/sudo` directly (no update survival); no license; redistributes a patched derivative of Apple's signed binary.

### mattrajca/sudo-touchid (sudo fork)
Forks `sudo 1.8.17p1`, registers a standalone `touchid` method ahead of PAM (and disables PAM), evaluating the undocumented `0x3f0` policy with a busy-wait `CFRunLoopRunInMode`. The localizedReason is the hardcoded `@"authenticate a privileged operation"`. **Strengths:** registering biometric auth as a standalone sudoers method is a clean low-surface integration point; `canEvaluatePolicy` gracefully disables when no sensor exists; the README's documented `LAPolicyDeviceOwnerAuthentication` test mode is a useful sensor-less dev affordance. **Weaknesses:** it is a **frozen 2016 sudo** missing all subsequent sudo CVE fixes; generic prompt; no console gate; no signing/SecAccessControl ACL; over SSH it *bricks* that sudo (no fallback); installed via `chmod 4755` + PATH-shadow, so a writable `/usr/local/bin` or hijacked PATH lets an attacker substitute a "sudo" the user is trained to approve.

### artginzburg/sudo-touchid (Bash installer / wrapper)
No auth code — it enables Apple's `pam_tid.so` and keeps it persisted. The exemplar for **OS-update survival**: writes `auth sufficient pam_tid.so` to `/etc/pam.d/sudo_local` on macOS 14+, or installs a `RunAtLoad` LaunchDaemon to re-apply the legacy `/etc/pam.d/sudo` edit on pre-14 systems; `--with-reattach` adds `pam_reattach.so` for the tmux/screen case. It also ships a clean `--disable` path that auto-detects and migrates legacy configs and writes a `.bak` backup before any in-place edit. **Strengths:** the most maintained project here (last commit 2026-05-03); installer-ownership hardening (mktemp → `sudo install -o root -g wheel`, with an `install-security.test.sh` asserting daemon targets are never written as the invoking user); safe-rollback via `.bak` backups and a clean `--disable`/migration path; `sw_vers` version-branching. **Weaknesses:** `curl | sh` bootstrap over a URL shortener with no checksum pinning (MITM → root-installed code); inherits all of `pam_tid`'s gaps (generic prompt, no console gate, fail-open); optionally loads a Homebrew-managed `pam_reattach.so` from a non-root-exclusive path into sudo's auth stack.

## How sudowhat differs

**(i) It renders the *resolved* command inside the system biometric prompt.** sudowhat passes the actual bytes sudo will `execve` — `command_info["command"]` plus `run_argv[]`, shell-quoted with control-characters escaped by name (`\n`, `\r`, `\t`, `\0`, `\\`) or hex (`\xNN`, `\uNNNN`) — as the `localizedReason` of `LAContext.evaluatePolicy` (`plugin/sudowhat_approval.m`, via `PromptFormatter`). **I checked the `showsResolvedCommand` field of all seven prior-art analyses; every one is `false`.** Apple's `pam_tid`, both pam-watchid variants, pam-touchID, pam_wtid, sudo-touchid (mattrajca), and artginzburg's installer all show a generic, install-time-fixed reason ("sudo is trying to …", "execute a command as root", `0x3f0`-policy default phrases) and none inspect the target argv. This is the exact gap the analyses name and sudowhat's reason for existing: it makes `sudo chown attacker:wheel /etc/sudoers` impossible to disguise behind a trustworthy-looking prompt.

**(ii) A console-user guard against reflexive-approval and SSH attackers.** Before prompting, sudowhat compares the invoking UID (from `user_info["uid"]`, stashed at `open()`) to the active console UID from `SCDynamicStoreCopyConsoleUser` (`plugin/SessionGuard.m`); a non-root UID that isn't the console user is **denied without prompting**, and the guard also rejects a console UID of `0` or `-1`. So an SSH session — or a second logged-in user, or a service account — cannot pop a Touch ID dialog that the person at the keyboard reflexively taps. **I checked the `consoleUserGuard` field of all seven analyses; every one is "No."** They either omit any session check entirely (mattrajca, Reflejo, biscuitehh, pam_wtid) or, at most, sniff `SSH_TTY`/`-A` env-and-argv flags (insidegui) — which is trivially spoofable and is *not* a binding to the console owner. Apple's `pam_tid` merely trusts LocalAuthentication's internal session binding rather than enforcing invoker == console user. None implement the property sudowhat does.

**(iii) It is an approval *plugin*, not merely a PAM auth enabler.** Every other project lives in the PAM `auth` stack (or inside a forked sudo's auth method), where it sees no command. sudowhat's gate runs as a sudo *approval plugin* (`SUDO_APPROVAL_PLUGIN`, type 4) loaded via `/etc/sudo.conf` *after* PAM, in sudo's `check` entry point — which is the only hook that receives `command_info[]` and `run_argv[]`. The architectural choice is what makes property (i) possible at all; the PAM family structurally cannot show the command because PAM is invoked before the command is resolved into the auth context.

**(iv) Mutual code-signature verification, fail-closed.** The two bundles verify each other: `pam_sudowhat` runs `SecStaticCodeCheckValidity` on the approval plugin (and confirms the `/etc/sudo.conf` Plugin line via `SudoConfChecker`) before returning `PAM_SUCCESS`; the approval plugin in turn verifies `pam_sudowhat.so` before trusting that the PAM step ran our code (`shared/SignatureVerifier.m`). A release build enforces a team-identifier requirement (`anchor apple generic and certificate leaf[subject.OU] = "<TEAM_ID>"`); dev/ad-hoc builds validate integrity only. The PAM wiring is `auth requisite pam_sudowhat.so` then `auth sufficient pam_permit.so`, and any failure of either component aborts sudo. **None of the prior art does any peer/self signature verification** — the entire field rests on filesystem permissions of an unsigned `.so` (or, for `pam_tid`, on SIP). And every PAM-family project is fail-*open*: a broken or removed module silently degrades to password. sudowhat is fail-*closed* by design — falling back to `pam_tid`-style permissiveness would be the regression it exists to fix.

**(v) No credential caching.** `/etc/sudoers.d/sudowhat` sets `Defaults timestamp_timeout=0`, so every privileged command re-prompts. This directly closes the `pam_tid` weakness the analysis flags: that sudo's ~5-minute timestamp silently covers subsequent invocations with no fresh consent. No prior-art project addresses the timestamp cache.

**(vi) A channel-binding verify nonce.** Before raising the sheet, sudowhat prints a short random code (`generate_verify_nonce`, a Crockford-base32 alphabet minus visually-ambiguous glyphs, ~20 bits) to the user's foreground terminal via sudo's `plugin_printf`, and embeds the same code in the prompt body. A genuine foreground `sudo` shows matching codes; a `sudo` spawned by a background process the user didn't initiate shows its code in some other terminal — or nowhere — letting the user reject before authenticating. It is a defense against absent-minded approval that complements, not replaces, the console guard. No prior-art project has any analogue.

**(vii) Prompt-spoofing hardening.** Because the prompt now carries attacker-influenceable bytes (argv), sudowhat treats the prompt text as a parsing boundary: control characters are escaped so a literal `\n` in argv cannot pose as a real newline and smuggle a fake second line into the sheet; ellipsis/spoof sequences are escaped; the rendered text is held under a conservative ~480-char budget below `LAContext`'s silent-truncation limit; and recognition aids like `TERM_PROGRAM`/`TERM` are explicitly documented as spoofable, with the nonce — not those strings — as the trust signal. The prior art, showing only static strings, never had to defend its prompt against its own input.

## Ideas worth adopting

- **`sudo_local` as the update-safe install surface — Apple `pam_tid` and artginzburg/sudo-touchid.** sudowhat already wires its PAM module through `/etc/pam.d/sudo_local` (which stock `/etc/pam.d/sudo` includes), so it inherits the update survival both of those projects rely on. Worth keeping as a hard invariant; the loudest complaint across the analyses is precisely the `/etc/pam.d/sudo` wipe.
- **A `RunAtLoad` LaunchDaemon re-applier as a pre-14 / belt-and-suspenders fallback — artginzburg.** sudowhat's `sudo.conf`/`sudoers.d` edits live outside `sudo_local`; if any future macOS rewrites those, artginzburg's idempotent boot-time re-apply pattern is a proven recovery mechanism.
- **Installer-ownership hardening + a security test that greps the installer — artginzburg.** Download to mktemp, then `sudo install -o root -g wheel -m …`, and ship a test asserting privileged targets are never written as the invoking user. sudowhat's roadmap (`sudowhat status`, Homebrew tap) would benefit from an equivalent `install-security` assertion.
- **A safe-rollback uninstall: `.bak` backups before in-place edits, plus legacy-config detection and migration — artginzburg.** artginzburg writes a `.bak` of any file before editing it and offers a clean `--disable` that auto-detects and migrates legacy configs. sudowhat touches four `/etc` files; backing each up before edit and detecting/migrating a prior install on `--disable` would make its uninstall as recoverable as its install.
- **Self-validating install with auto-rollback — inickt/pam_wtid (`make working`) and sudowhat's own rollback.** sudowhat already "rolls back on any failure"; adopting pam_wtid's *positive* post-install smoke test (exercise a real `sudo -k && sudo /bin/echo` and auto-uninstall on failure) would guarantee the user is never left with a broken sudo — the highest-stakes failure mode for anything in this category.
- **A fixture set of OS-version artifacts — inickt/pam_wtid.** pam_wtid keeps real `pam_tid` binaries from multiple macOS versions and tests against each. sudowhat depends on `SecStaticCode` behavior, the `LAContext` truncation budget, the BiometricsOrCompanion policy availability, and sudo's plugin ABI — a pinned fixture/CI matrix across macOS releases would catch silent drift (the README already flags the budget as "measured in English only" and untested across locales).
- **Prearm the biometric sensor — Apple `pam_tid` (`prearmTouchIdWithReply:`).** Apple's module prearms the sensor before the `LAContext` sheet appears, cutting perceived latency. sudowhat currently calls `evaluatePolicy` cold (`plugin/sudowhat_approval.m`); issuing a prearm call as soon as the console-user guard passes — before the prompt text is even assembled — would shave the same startup latency without changing the security model.
- **Detect non-interactive / askpass invocations up front and bail cleanly — the Swift family (insidegui, Reflejo, biscuitehh).** These modules inspect `-A`/`--askpass` (and, for insidegui, `SSH_TTY`) and return `PAM_IGNORE` rather than raising a sheet that can never be answered. sudowhat substitutes a console-user guard but has no explicit `-A`/`--askpass` handling; detecting an askpass/non-interactive invocation and declining cleanly — instead of relying on the guard alone — would avoid surprising a script that expected a password channel.
- **Implement and explicitly `PAM_IGNORE` the unused PAM entry points — insidegui/pam-watchid.** insidegui defines all four PAM entry points and has the unused ones return `PAM_IGNORE` so the module is well-behaved in the stack. `pam_sudowhat.m` implements only `pam_sm_authenticate` and `pam_sm_setcred`; adding explicit `PAM_IGNORE` stubs for `pam_sm_acct_mgmt` and `pam_sm_chauthtok` is cheap stack hygiene.
- **The `0x3f0` / private-options insight, as a documented pitfall — inickt and the Swift forks.** pam_wtid's author documented *why* naive Swift `LAContext`-as-root mis-binds the user ("no fingerprints enrolled"). sudowhat solves the same hazard differently and correctly — `seteuid(g_inv.uid)` around `evaluatePolicy` so canEvaluate/biometric/companion resolve against the user's enrollment — but the failure mode is worth citing in sudowhat's own docs as the reason the EUID drop exists.
- **A documented password-dialog test mode — mattrajca.** mattrajca's README swap to `LAPolicyDeviceOwnerAuthentication` lets you verify the LA plumbing on sensor-less hardware. sudowhat's tiered `BiometricsOrCompanion → DeviceOwnerAuthentication` selection already degrades to password; exposing an explicit "force password path" test toggle would aid CI on machines without Touch ID.
- **`canEvaluatePolicy`-first gating with graceful selection — the whole PAM family.** sudowhat already does this (prefer BiometricsOrCompanion, fall back to DeviceOwnerAuthentication, deny only if neither evaluates). The field-wide convention validates the approach.
- **`pam_reattach` awareness for tmux/screen — artginzburg.** sudowhat's console-user guard binds to the GUI session; the tmux/screen audit-session detach that historically broke `pam_tid` could interact with that gate. Worth a documented test and, if needed, a `pam_reattach` interop note.

## Risks & criticisms of sudowhat surfaced by this comparison

**The SSH gap is a hard denial, not a graceful fallback — and that's a defensible point of contention.** insidegui/pam-watchid, biscuitehh, Reflejo, and Apple's `pam_tid` all return `PAM_IGNORE` over SSH so the user transparently gets a password prompt. sudowhat's console-user guard instead *denies* a non-console UID without prompting (`SessionGuard.m`). That is the correct security posture against the reflexive-approval threat — but it means a legitimate remote admin over SSH gets a hard "not in active GUI session" denial rather than a password fallback. The PAM family made the opposite, lower-friction trade. sudowhat's fail-closed stance is principled, but the comparison makes clear it is *less convenient by design*, and the root-caller exemption (uid 0 bypasses the gate, logged to authpriv) is the one pressure valve — a deliberate hole that the README justifies but that a reviewer should weigh.

**Complexity and maintenance burden vs. a one-line `pam_tid` enable.** The entire competing field is either ~65–100 lines of Swift or, in artginzburg's case, an installer around Apple's *own* module. sudowhat is ~1,100 LOC of hand-written Objective-C/C implementation (~1,369 LOC counting headers and the vendored Apple `sudo_plugin.h` ABI header, the figure the project's own `docs/language-choice.md` cites) across two mutually-verifying bundles plus a PAM module, a sudo-plugin, signature verification, a prompt formatter with surrogate-pair index arithmetic, and four installed `/etc` files. That is materially more attack surface and maintenance load *inside setuid-root sudo* than `auth sufficient pam_tid.so`. The justification — only an approval plugin can see the command — is sound, but the cost is real: a sudo approval-plugin ABI is more niche and less documented than the PAM `auth` ABI the rest of the field targets, and sudowhat carries a self-documented TOCTOU window (re-stat by `(dev,inode)`, but no `fexecve` on macOS) that the simpler enablers don't even have to reason about because they never resolve the command.

**Objective-C/C over Swift — sudowhat's choice is well-argued, but it's swimming against the community.** Four of the prior-art modules are Swift, and Swift PAM modules are the documented norm (the `language-choice.md` doc cites biscuitehh/pam-watchid itself as precedent). sudowhat's rationale is strong and specific: sudo's approval-plugin ABI requires an exported C *global* (`@_cdecl`/`@c` cover functions only), and injecting the Swift runtime into setuid-root sudo and a multi-plugin PAM host is exactly the hazard Apple's DevRel warns against. The criticism the comparison surfaces is narrower: the one component that would genuinely benefit from Swift's `String` — `PromptFormatter`, the anti-spoofing boundary with hand-rolled `unichar` index math — stays in ObjC, where a surrogate-pair or unsigned-wrap bug is a live class. sudowhat mitigates with unit tests (`make test-unit`), which the Swift forks mostly lack, so this is defense-in-depth foregone on already-memory-safe code rather than a present defect.

**Dev-mode integrity-only signing weakens property (iv) in practice.** sudowhat's mutual signature verification is its strongest differentiator, but the shipped default is ad-hoc signing, under which *any* validly-signed bundle passes — substitution with a different signed binary is undetected (the README is candid about this). Until the Developer-ID release build lands, sudowhat's tamper-resistance advantage over the unsigned field is "broken signatures are caught," not full authorship enforcement. Several prior-art projects also rely solely on `root:wheel` 444 permissions; in ad-hoc mode sudowhat's real-world margin over them is thinner than the release-build story implies.

**Per-command re-prompting (`timestamp_timeout=0`) is a security win that doubles as a usability tax.** Disabling the cache closes the `pam_tid` "one tap covers five minutes" hole, but the rest of the field deliberately keeps sudo's cache for ergonomics. Combined with no SSH fallback and no command-context caching, sudowhat asks for a fresh biometric on *every* privileged command — correct for the threat model, but the comparison makes explicit that sudowhat trades away the convenience that motivated most users to install a biometric-sudo tool in the first place.
